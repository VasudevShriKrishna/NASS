# NASS Group & Sarvam AI Document Intelligence: Single-Call Vision Extraction Specification

## 1. Executive Summary & Architectural Understanding

### 1.1 The User's Core Intent & Directives
The objective is to introduce an enterprise-grade document extraction capability powered by Sarvam Vision into the existing NASS Control Tower application strictly via the Sarvam MCP architecture.

Key non-negotiable principles:
1. **Single-Call Vision Extract Rule:** Exactly one `sarvam_vision_extract` call per document (or ≤10-page batch) using a complete, strongly-typed JSON schema. **Zero chaining of multiple MCP tools** and **no separate digitise + extract pipeline** (do not call `sarvam_vision_digitise` first).
2. **Strict Limit Enforcement:**
   - **Page Cap:** Maximum 10 pages per batch.
   - **File Size Cap:** Maximum 200 MB.
   - **Rate Limiting:** Maximum 10 requests per minute sliding window.
3. **Format-Aware Routing:**
   - **Vision Eligible:** PDF, PNG, JPEG, TIFF, WEBP.
   - **Non-Vision Formats:** `.docx` (parse/extract locally), `.xlsx` / `.csv` (parse structured tabular data directly). **Never transmit non-Vision formats to Sarvam Vision.**
4. **Honesty & Anti-Fabrication:**
   - Missing fields must return `null` or `"not found"`.
   - Never hallucinate or synthesize absent values.
   - Distinct classification between:
     - `field_not_found` (field genuinely absent from document)
     - `connector_error` (network, rate limit, quota, or authentication failure)
     - `model_error` (schema mismatch or inference exception)
5. **Non-Invasive Architecture:**
   - Exactly **one isolated module**: `src/lib/sarvam/vision-extractor.ts`.
   - Exactly **one additive entry point**: `src/app/api/documents/extract/route.ts`.
   - Gated behind a feature flag (`SARVAM_VISION_EXTRACTION_ENABLED`, defaults to enabled).
   - API key read strictly from existing configuration (`process.env.SARVAM_API_KEY`, cookies, headers) — never hardcoded.
   - Zero modifications to unrelated routes, databases, or UI components.

## 2. Master Implementation Prompts & Sub-Prompts

### Prompt 1: Master Specification & Core Isolation
```markdown
Implement an enterprise-grade Document Intelligence extraction service powered by Sarvam Vision using the Sarvam MCP standard.
Isolate all core logic in `src/lib/sarvam/vision-extractor.ts`.
Do not touch existing database tables or Prisma schema.
Ensure the module reads credentials dynamically from `process.env.SARVAM_API_KEY`, request cookies (`sarvam_api_key`), or request headers (`x-sarvam-key`).
Enforce the feature flag `SARVAM_VISION_EXTRACTION_ENABLED`.
Enforce a sliding-window rate limit of 10 requests/minute, a file size cap of 200 MB, and a page limit of 10 pages per batch.
```

### Prompt 2: Single-Call Schema-Based Extraction Engine
```markdown
Define complete, self-contained JSON Schemas for trade documents:
- PURCHASE_ORDER (po_number, po_date, buyer, supplier, line_items, totals, incoterms)
- BILL_OF_LADING (bol_number, carrier, vessel, voyage, shipper, consignee, ports, cargo, weights)
- COMMERCIAL_INVOICE (invoice_number, invoice_date, seller, buyer, currency, totals, payment_terms)
- MILL_TEST_CERT (heat_number, grade, standard, yield_strength, tensile_strength, chemical_composition)
- GENERIC (key-value schema)

Execute exactly one `sarvam_vision_extract` call per batch containing the document base64 and the complete schema.
Never invoke `sarvam_vision_digitise` prior to extraction.
```

### Prompt 3: Format-Aware Guardrails & Non-Vision Parsers
```markdown
Inspect the input MIME type and file extension before invoking external APIs.
If the document is a `.csv` or `.xlsx`:
- Read rows and columns directly via local parser.
- Extract headers and key fields deterministically.
- Do NOT invoke Sarvam Vision.
If the document is a `.docx`:
- Decompress and parse `word/document.xml` locally using Node built-in zlib.
- Extract text content, tables, and paragraphs.
- Do NOT invoke Sarvam Vision.
If the document is a PDF:
- Parse page tree / catalog to count pages.
- Reject or batch if > 10 pages.
- Enforce <= 200 MB.
```

### Prompt 4: Anti-Fabrication & Error Disambiguation Layer
```markdown
Establish a strict verification contract:
Every extracted field must include a status metadata tag:
- 'extracted': value found in document and parsed.
- 'field_not_found': field is absent from document (value must be null or "not found").
- 'connector_error': network/rate-limit/auth failure occurred.
- 'model_error': schema or inference exception occurred.
Never fabricate synthetic dates, amounts, or supplier names.
```

### Prompt 5: Additive HTTP Entry Point & Verification Suite
```markdown
Create `src/app/api/documents/extract/route.ts` supporting both GET (capabilities and status) and POST (document upload / extraction).
Write a comprehensive test suite `tests/vision-extractor.test.ts` validating:
1. Feature flag gating.
2. 10 req/min rate limiter.
3. 200 MB limit enforcement.
4. 10 page limit enforcement.
5. Non-Vision handling (.csv, .xlsx, .docx).
6. Single-call Sarvam Vision extraction.
7. Anti-fabrication guarantees.
Confirm all existing Control Tower functions and routes are 100% unaffected.
```
